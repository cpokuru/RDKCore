Component Registry

The authoritative record of every RDK-B component -- registration, lifecycle state, and ownership, per §7.3.2 of the Core RDK Broadband Specification.

§7.3.2 Component Registry§7.3.3 Lifecycle States
Registry policy · §7.3.2 & §7.3.3

What "registered" means

Every component merged into RDK-B is entered here at merge time. This is a summary of the governing rules, not the full spec text -- see the Component Governance section of Development Standards for the complete wording.

Catalog schema & controlled vocabulary

The fields, identifiers, lifecycle states, classification rules, and profile-applicability model below are the schema every entry must follow -- decided once, here, before components are loaded, so a catalog that grows past today's 78 entries doesn't end up classified inconsistently by whoever happens to be filling it in. Tier and category are the controlled vocabulary: a fixed, pre-designated set of classification values -- profile applicability, core/non-core status, category -- applied the same way to every component, not chosen freely per entry.

Registering a new component · §7.2.3.1 & §7.2.4.1

A new component is any new open source repo or group of repos adding new RDK-B features or services. It must be organized as one logically self-contained, includable/excludable unit -- not a grab-bag of unrelated functionality.

Scope & ownership

Problem statement, functional scope, ownership, which profiles it applies to

Interfaces & data

Data models provided and consumed, HAL APIs used, build/runtime dependencies

Impact

Security, telemetry, logging, memory/CPU, boot-time, restart/recovery behavior

Delivery

Test plan, platform portability, release target, rollback plan

The flow · §7.2.8.1
Step 1

Propose -- open an architecture proposal ticket and identify an owner

Step 2

Define -- interfaces, dependencies, HAL/OSS usage, and every data model provided or consumed

Step 3

Build -- implement, run unit tests, validate on the reference platform

Step 4

Submit -- open a PR, pass CI, complete peer review (and RTAB review if required)

Step 5

Merge -- attach test evidence; merge only after a sanity pass against run-time data model auto-discovery

Step 6

Register -- entered into this registry at merge time; track through the next release

What the registry itself tracks · §7.3.2.1

Identity

Name, repositories, per-profile classification (CORE / Required / Optional)

Ownership

Primary and secondary owner, name and organization

Interfaces

RBUS / HAL, HAL contract reference, TR-181 data model

Dependencies

Dependent RDKB components and non-RDKB open source components

Health

Last validated release, open critical issues, distro flags

Lifecycle states · §7.3.3
ActiveActive development. New features and fixes accepted.
StableInterface frozen. Critical/security fixes only.
DeprecatedScheduled for removal. Migration path published.
RemovedNo longer part of RDK-B. Repository archived.

Each forward transition requires architecture-owner or RTAB approval; deprecation requires a published migration path before a component can move to Removed.

Maintenance · §7.3.2.2
  • Updated at every release; any owner, state, or interface change must trigger an update
  • RTAB owns registry accuracy and the registry must stay publicly accessible
